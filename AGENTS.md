# chopcheck-support

Бот поддержки ChopCheck на `support.chopcheck.ru`. Принимает обращения в личных сообщениях и зеркалит их в форумные темы рабочей группы, где с ними работают операторы.

Этот файл — рабочий контекст для агентов: то, чего нельзя вывести из кода. Карта организации — в `AGENTS.md` репозитория `compass`.

## Он ничего не знает про ChopCheck

Единственный сервис организации, который **не связан ни с чем остальным**. Он не ходит ни в `chopcheck`, ни в `auth`, ни в общую базу. Пользователь для него — это телеграм-аккаунт и ничего больше; сопоставления с аккаунтом ChopCheck нет.

Из общей инфраструктуры он берёт только Redis. База — своя SQLite в томе.

Бот тоже отдельный — `@chopcheck_support_bot`, со своим токеном. Он не тот же, что бот Mini App.

Единственный Python-сервис организации. Всё остальное — Bun/TypeScript и Go.

Репозиторий — **настоящий GitHub-форк** `zavul0nn/support-bot` (MIT, Shon Ness, 2024). Бейдж в README при этом указывает на `mrtesla07/support-bot` — это след более ранней истории, а не текущий родитель. Апстрим — универсальный бот поддержки, изначально сделанный под VPN-сервис.

## Состояние переехало из Redis в SQLite

Раньше всё состояние — пользователи, тикеты, FAQ, настройки, напоминания — лежало в Redis. Сейчас оно в SQLite (`SQLITE_PATH`, том `support-bot-data`), а Redis остался под FSM-состояния диалогов.

Миграция **уже выполнена**: в проде `REDIS_MIGRATE_ON_START=false`. Импорт из Redis одноразовый и защищён флагом в самой базе, но включать его обратно без причины не надо.

**`docs/DEVELOPMENT.md` устарел** — там всё ещё написано, что Redis это основное хранилище состояния. Верь коду и этому файлу.

Данные бота живут в томе `support-bot-data`, а не в общем Postgres. В бэкап они попадают: `shared/scripts/backup.sh` в `infrastructure` отдельной строкой вытаскивает файл базы из контейнера через `docker cp chopcheck-support-bot:/data/support-bot.sqlite3`. Переименуешь контейнер или переедешь с этого пути — молча сломаешь бэкап, скрипт про SQLite знает жёстко зашитыми значениями.

## В проде он работает на polling, а не на вебхуках

Telegram заблокирован на сетевом уровне, и блокировка **симметричная**: сервер не только не может достучаться до Telegram, но и Telegram не может достучаться до сервера. Вебхук просто не доставляется.

Поэтому в проде стоит `BOT_MODE=polling` — бот сам вытягивает апдейты наружу через прокси. `WEBHOOK_URL=https://support.chopcheck.ru` в окружении при этом остался и никак не используется.

Код по умолчанию считает режимом `webhook`, так что prod-конфигурация выглядит как отклонение. Это не отклонение, а необходимость — подробнее в `AGENTS.md` репозитория `compass`, раздел про телеграм-прокси.

В режиме polling рядом всё равно поднимается крошечный aiohttp с `/health` — иначе docker healthcheck не за что зацепиться.

## Как устроена работа с обращением

```text
пользователь пишет в личку боту
        ↓
создаётся отдельная форумная тема в группе поддержки
        ↓
сообщения и медиагруппы зеркалятся в обе стороны
        ↓
оператор работает в теме: инлайн-панель, /resolve, /silent, /ban
```

Тема на пользователя одна и переиспользуется. `BOT_GROUP_ID` — та самая группа-форум; без неё бот бесполезен.

Медиагруппы собираются middleware `album.py`: Telegram присылает альбом отдельными апдейтами, и без сборки в группу они уедут в тему по одной картинке.

Напоминания о «висящих» обращениях крутит APScheduler внутри процесса — отдельного воркера нет.

Есть антиспам: фильтр ссылок и инвайтов, санитация имён, автобан подозрительных профилей. Включается `SECURITY_FILTER_ENABLED`, в проде включён.

## Локальная разработка

```bash
pip install -r requirements.txt
python -m app
```

Python 3.12.

Что нужно задать:

- **свой тестовый бот** — боевой токен брать нельзя, два процесса на одном токене отбирают друг у друга апдейты;
- **свою группу-форум** и её `BOT_GROUP_ID`, плюс `BOT_DEV_ID` — свой телеграм-id, без него не работают админ-команды;
- `BOT_MODE=polling`, иначе бот попытается зарегистрировать вебхук на несуществующий адрес.

Redis нужен, Postgres — нет. SQLite создаётся сам по пути из `SQLITE_PATH`.

Тесты — `pytest`, они же гоняются в CI. Это единственный сервис организации с тестами на Python.

## Прод

Один контейнер `chopcheck-support-bot` в стеке `chopcheck`, один образ без таргетов. Caddy отдаёт `support.chopcheck.ru` на порт 8080 — но в режиме polling там живёт только `/health`.

Выкладка — ручной запуск `Deploy` в `infrastructure` с целью `chopcheck`, которая заодно перезапустит и весь остальной стек. Процедура в `.agents/skills/deploy/SKILL.md`.
